# Passive multi-view Apple fingerprinting beyond RFB/5900

**Search date:** 2026-09-01
**Question:** Which passive, local or network-adjacent evidence can identify an Apple device category or an explicit hardware model when Screen Sharing/RFB is disabled, and which collection paths are safe to add to this macOS CLI?

## Executive answer

RFB is a sparse, optional view, not a suitable discovery anchor. Apple documents that Screen Sharing must be turned on before another Mac can connect and that Mac screen sharing uses TCP 5900 by default ([Screen Sharing settings](https://support.apple.com/en-ie/guide/mac-help/mh11848/mac), [port documentation](https://support.apple.com/en-gb/guide/mac-help/mchl67d5398b/mac)). When Screen Sharing and Remote Management are off, `_rfb._tcp` should be expected to disappear; iPhone, iPad, Apple TV, and HomePod are outside this Mac-only feature in any case. A service or port at 5900 also describes a VNC/RFB capability, not a hardware model, and non-Apple VNC servers use the same default port.

The best safe default is therefore **broader DNS-SD collection plus conservative fusion**:

1. enumerate advertised service types dynamically with the RFC 6763 `_services._dns-sd._udp.local.` meta-query, then resolve only bounded DNS-SD records;
2. retain the high-yield Apple-related families already seen in practice (`_device-info`, AirPlay/RAOP, and companion-link) and add public HomeKit semantics where relevant;
3. give an exact-model result only to a sanitized, explicitly advertised identifier such as `Mac17,9` that is recognized by a provenance-bearing catalog;
4. use all other views—service families, DHCP shape, SSDP, name-resolution protocols, OUI, timing, and radio presence—only for vendor/category/consistency evidence; and
5. never fetch an SSDP `LOCATION`, open a discovered port, or otherwise interrogate an application endpoint.

This is a rules-and-evidence design, not a recommendation to transplant a machine-learning classifier. Large studies show why multiple broadcast/multicast views improve coverage and expose inconsistent spoofing, but their trained labels do not transfer automatically to this repository's small, Apple-focused corpus. Yu et al.'s OWL used DHCP/DHCPv6, mDNS, SSDP, LLMNR/BROWSER/NBNS, other UDP, protocol sequence, and MAC-prefix views over more than 30,000 devices ([USENIX Security 2020 paper](https://www.usenix.org/system/files/sec20-yu.pdf)). IoT Sentinel classified device types from initial traffic ([original paper](https://arxiv.org/abs/1611.04880)), while AuDI learned periodic communication patterns rather than explicit identities ([author-institution copy](https://acris.aalto.fi/ws/portalfiles/portal/32146255/AuDI_Aalto.pdf)). These establish feasibility, not safe exact-model rules for current Apple products.

## Search and selection method

### Sources and queries

Searches were run on the RFC Editor, Apple Developer and Apple Support, Apple open-source GitHub repositories, USENIX proceedings, IEEE/ACM metadata or author-institution repositories, and the public web index. Representative queries were:

- `RFC 6762 passive observation cache flush TTL`, `RFC 6763 _services._dns-sd._udp meta-query TXT`;
- `Apple Bonjour PTR SRV TXT`, `mDNSResponder dns_sd.h IncludeP2P IncludeAWDL`;
- `Apple AirPlay deployment _airplay._tcp _raop._tcp`, `Apple Screen Sharing 5900`;
- `HomeKitADK HAPIPServiceDiscovery _hap._tcp TXT ci md`;
- `DHCP vendor class client identifier hostname parameter request list`, `DHCPv6 vendor class RFC 8415`;
- `UPnP Device Architecture SSDP NOTIFY`, `RFC 4795 LLMNR`, `RFC 1002 NBNS`, `RFC 4861 NDP`;
- `You Are What You Broadcast USENIX 2020`, `Stute AWDL USENIX 2019`, `Stute Continuity USENIX 2021`;
- `IoT Sentinel original paper`, `AuDI autonomous IoT device-type identification`; and
- `Apple private Wi-Fi address random MAC`, `IEEE OUI universal local bit`.

### Inclusion and exclusion

Included sources had to be one of: an IETF RFC; current Apple developer/support documentation; Apple-maintained open source; an original peer-reviewed/conference paper; or an official author/institution repository for that paper. A source also had to support a concrete protocol, platform-access, inference, or privacy claim in this note. Seminal specifications were retained regardless of age because the on-wire format remains normative. Product/platform documentation was checked as of the search date.

Excluded were service-list aggregators, scanner-vendor fingerprint databases, blogs, reverse-engineering summaries without an original artifact, forum anecdotes, and secondary citations where an RFC, Apple page/source file, conference paper, or author copy was available. Undocumented Apple TXT semantics were not promoted to facts merely because third-party implementations agree. In particular, public Apple material confirms the AirPlay service types, but does not publicly standardize every current AirPlay/RAOP TXT key; the `am`/`model` interpretation below is therefore bounded by explicit local observation and catalog recognition rather than represented as an AirPlay standard.

### Limitations

- Apple service advertisements and Continuity payloads vary by OS release, settings, sleep state, interface, and ecosystem activity. Absence during a bounded scan is not evidence of absence.
- Wi-Fi client isolation, multicast filtering, VLANs, switches, sleep proxies, and capture position change which broadcast/multicast traffic is visible. RFC 6762 also permits opportunistic caching and TTL-based persistence, so a record can briefly outlive a device ([RFC 6762](https://www.rfc-editor.org/info/rfc6762/)).
- Several Apple upper-layer protocols are proprietary. The AWDL/Continuity papers are careful reverse-engineering studies, not vendor specifications, and examined older OS versions.
- The empirical fingerprinting papers evaluate their own populations and labels. Their accuracy estimates must not be applied to Apple models absent a new, representative, versioned ground-truth corpus.
- This review did not perform a new radio experiment or validate every service on every current Apple device. The single live-scan result below is project-local evidence, not a general prevalence estimate.
- `Mac17,9` is an explicit model identifier, but Apple's current identification page maps `Mac17,7` and `Mac17,9` to the same product family, “MacBook Pro (14-inch, M5 Pro or M5 Max)” ([Apple's model list](https://support.apple.com/en-gb/108052)). A catalog should not claim a finer chip configuration unless a primary source distinguishes it.

## Collection planes and access boundaries

“Passive” needs two meanings here. A DNS-SD browser sends browse/resolve queries but does not connect to the advertised application service; call this **non-interrogating discovery**. A packet collector that sends nothing is **wire-passive**. The CLI and output should report which mode produced each observation instead of conflating them.

| Plane | Typical evidence | Current/default availability | Privilege and permission boundary | Backend implication |
|---|---|---|---|---|
| Infrastructure-link Bonjour | mDNS on the joined Ethernet/Wi-Fi link: service PTR, SRV, TXT, A/AAAA; fixed and dynamically enumerated types. | Yes, using the current `python-zeroconf` path; it emits DNS-SD queries but opens no service connection. | No root. On macOS 15, Terminal/SSH-launched command-line tools are automatically allowed; a packaged responsible app may need Local Network consent and Bonjour declarations under [TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy). | Existing backend can remain the default; add meta-enumeration and richer record metadata. |
| Wire-passive LAN capture | DHCP/DHCPv6, mDNS, SSDP, LLMNR, NBNS, ARP/NDP, timestamps and packet co-occurrence. | No; optional only. Visibility depends on broadcast delivery/capture position. | Apple's packet-trace guidance uses privileged `tcpdump`; raw capture should be treated as root-required and explicitly enabled. | New capture/parser backend; never retain full pcap by default. |
| Apple P2P / AWDL DNS-SD | Bonjour services on peer-to-peer interfaces, including Continuity/AirDrop activity. | Not through the current pure-Python socket browser. | Native system browsing does not inherently require root, but still has local-network/privacy context; discoverability is activity/settings dependent. Raw 802.11 monitor capture is out of safe default scope. | A native DNS-SD backend is required to set `kDNSServiceFlagsIncludeP2P` and/or `kDNSServiceFlagsIncludeAWDL`; Apple's header says `InterfaceIndexAny` excludes P2P by default. |
| BLE proximity | Apple manufacturer advertisements, Continuity activity class, nearby accessory advertisements. | No; must be opt-in and proximity-scoped. | CoreBluetooth requires Bluetooth permission and a usage description in a bundled program ([Core Bluetooth](https://developer.apple.com/documentation/corebluetooth), [`NSBluetoothAlwaysUsageDescription`](https://developer.apple.com/documentation/BundleResources/Information-Property-List/NSBluetoothAlwaysUsageDescription)). | Prefer a small signed native helper/app-host; a plain pip CLI has poor consent UX. Do not connect or read GATT characteristics. |

BLE, AWDL, and infrastructure Bonjour are not interchangeable. BLE is low-bandwidth proximity advertisement and commonly bootstraps discovery. AWDL is an Apple peer-to-peer Wi-Fi link layer. DNS-SD/mDNS can run over AWDL, while ordinary infrastructure Bonjour runs over the joined LAN. Stute et al. observed AirDrop using BLE to activate AWDL and then mDNS/DNS-SD over AWDL ([2019 paper](https://www.usenix.org/system/files/sec19-stute.pdf)); their later work observed Handoff/Universal Clipboard using BLE plus an AWDL `_companion-link` browse ([2021 paper](https://www.usenix.org/system/files/sec21-stute.pdf)). Apple's own native API keeps these interfaces opt-in through separate flags.

## Inference contract

The output should expose evidence and rule results separately. The following rules are intentionally stricter than a statistical fingerprinting system.

1. **Exact hardware requires explicit recognized data.** A model result may be emitted only when a DNS-SD TXT value (or a future equivalently explicit public field) exactly matches a catalog key after bounded normalization, and that catalog entry cites a primary model source. For example, `Mac17,9` is recognized by Apple's model page; `_rfb._tcp:5900`, “MacBook Pro” in a name, an Apple OUI, AirPlay presence, or a learned packet pattern is not an exact identifier.
2. **Preserve identifier granularity.** Report `identifier: Mac17,9` and the narrowest product family the primary catalog supports. Do not infer chip, memory, size, color, serial, OS version, or owner.
3. **Other views are category/vendor/consistency only.** Service families, HomeKit `ci`, DHCP/SSDP tokens, LLMNR/NBNS, OUI, timing, BLE, and AWDL can vote for categories, vendor compatibility, or “inconsistent,” never an exact Apple model.
4. **Scope every claim.** Evidence stores interface, network plane, observation time, service/record/key, and whether it came from a query-based browser or wire-passive capture. A P2P observation is not silently merged with an infrastructure observation merely because names resemble each other.
5. **Handle conflict before confidence.** Two distinct recognized model identifiers for a correlated device force `model: unknown`, preserve both candidates and sources, and add a high-severity conflict. A recognized identifier conflicting with strong category evidence also downgrades the category and marks inconsistency. Agreement across `_airplay` and `_raop` increases consistency but cannot authenticate either record.
6. **Treat network text as attacker-controlled.** Bound lengths/counts, retain bytes safely, sanitize terminal/JSON output, implement first-key semantics for duplicate TXT keys as RFC 6763 requires, and never evaluate or dereference values.
7. **Be conservative when correlating.** Within one scan, an identical resolved SRV target plus overlapping address and interface is useful. Address alone is weak because DHCP churn, NAT, proxies, sleep proxies, and reuse exist. A locally administered/random MAC must not become a durable identifier. Ambiguous joins stay as separate records.
8. **Absence is usually missing evidence.** No RFB means “Screen Sharing not observed,” not “not a Mac.” No DHCP during ten seconds means “lease exchange not observed,” not “not Apple.” No BLE/AWDL means only that no eligible activity was visible under current permissions/settings.
9. **Never interrogate services.** The implementation may issue bounded DNS-SD browse/resolve queries. It must not connect to 5900 or any advertised port, send SSDP `M-SEARCH`, fetch an SSDP `LOCATION`, initiate ARP/NDP/LLMNR/NBNS probes, activate AWDL peers, connect over BLE, read GATT, pair HomeKit, or send companion-link system-info requests.
10. **Unknown is a successful result.** If explicit recognized data is absent or contradictory, emit category/vendor evidence with `model: unknown`; do not backfill from a heuristic or nearest catalog string.

### Concrete local case: `10.147.17.140`

In the project's bounded live scan on 2026-09-01, the same locally resolved device view at `10.147.17.140` advertised `_airplay._tcp` with **`model=Mac17,9`** and `_raop._tcp` with **`am=Mac17,9`**. That would identify the explicit identifier `Mac17,9` even if `_rfb._tcp` is absent, and Apple's current model page associates `Mac17,9` with the 2026 14-inch MacBook Pro M5 Pro/M5 Max family ([Apple Support](https://support.apple.com/en-gb/108052)).

This is a **local, bounded, spoofable observation**, not proof that the sender is genuine Apple hardware or that every `Mac17,9` advertises those keys. The safe output is an exact identifier candidate with two agreeing TXT sources, the Apple-supported product-family mapping, an explicit “unauthenticated self-advertisement” caveat, and the scan/interface timestamp. It must not claim a particular chip variant. If a third service advertises another recognized identifier, the result becomes `unknown` with a conflict. This new observation also supersedes the earlier RFB-only fixture's evidentiary situation: RFB alone remained model-unknown; AirPlay/RAOP supplied the explicit fields.

## Prioritized implementation roadmap

### Phase A — safe default: broader DNS-SD and evidence fusion

**Goal:** maximize non-interrogating infrastructure-link coverage without root, radio permissions, or endpoint connections.

1. Refactor `src/bonjour_fingerprint/discovery.py` behind a small `ObservationBackend` protocol and keep `ZeroconfBackend` as default. Add a bounded service-type enumerator for `_services._dns-sd._udp.local.`. Start with the fixed Apple list immediately, merge dynamically advertised types, validate the `_name._tcp|_udp.local.` shape, cap types and instances, and share the scan deadline so a hostile responder cannot extend runtime.
2. Add `_hap._tcp.local.` to the documented profiles and let dynamic enumeration reveal unknown types. Keep `_device-info`, `_airplay`, `_raop`, `_companion-link`, and `_rfb`; do not remove RFB, but label it optional capability evidence.
3. Extend `ServiceObservation` in `models.py` (or add `records.py`) with `observed_at`, `expires_at`/TTL when available, interface/index, `plane` (`infrastructure`, `p2p`, `awdl`, `ble`), and `collection_mode` (`dnssd-query`, `wire-passive`). Preserve normalized record/key provenance rather than flattening all `am`, `model`, and `md` into equivalent semantics.
4. Split `fingerprints.py` into declarative `profiles.py` and a small `inference.py`. A profile specifies service type, allowed exact-ID keys, category-only fields, and public source URL. Allow `am`/`model` exact candidates only when the catalog recognizes the entire value. Interpret HomeKit `ci` and `md` under HomeKit semantics; do not treat HAP `md` as an Apple-computer identifier.
5. Add provenance to `data/apple_models.json` or replace each value with `{name, identifiers, source_url, checked_at}`. Correct the `Mac17,9` mapping to the granularity Apple actually documents. Reject catalog entries without a primary URL in tests.
6. Add CLI/output fields: `collection_planes`, `collection_mode`, `catalog_source`, `spoofable: true`, and structured `conflicts`. Keep the default command free of `--connect`, `--fetch`, or any fallback probing.

**Tests:** meta-query empty/fallback; dynamic type added/removed; cap/deadline; malformed and duplicate TXT; mixed binary values; same explicit ID across AirPlay/RAOP; conflicting recognized IDs; HAP `ci` category and HAP `md` not exact Apple hardware; RFB absent with explicit AirPlay model; unrecognized identifier remains unknown; correlation ambiguity; IPv6 address retention; deterministic sanitized output; monkeypatch sockets to assert no TCP connect, URL open, SSDP send, or subprocess probe.

This phase is the highest-value change because the current fixed list is the main avoidable blind spot. It also directly solves the local `10.147.17.140` case without privileged capture or proximity surveillance.

### Phase B — optional wire-passive packet capture

**Goal:** add independent consistency views for operators who explicitly accept privileged capture.

1. Add `capture.py` and parsers under `parsers/{dhcp,ssdp,names,neighbors}.py`, selected by `scan --passive-packets --interface …`. Refuse silent privilege escalation; explain that the user must run in an authorized environment. Use a narrow BPF covering DHCPv4/v6, mDNS, SSDP, LLMNR, NBNS, ARP, and essential ICMPv6 NDP rather than collecting arbitrary unicast payloads.
2. Normalize only the required fields into new view observations. Parse DHCP option presence/order and bounded values; unsolicited SSDP `NOTIFY` headers but not HTTP bodies; LLMNR/NBNS names; ARP/NDP associations; packet timestamp and direction. Never send discovery packets.
3. Default to **no pcap file** and no raw payload persistence. Hold raw packets only until parsing, omit DHCP client IDs/DUIDs, HAP IDs, full MACs, and personal names from normal output, and hash ephemeral correlation keys with a per-run salt kept only in memory.
4. Add a `FusionWindow` in `aggregator.py` that correlates only within a short session and exposes reasons/ambiguity. Co-occurrence can raise category consistency or conflict; it cannot promote an exact model. Do not add a learned classifier until a separately reviewed, representative Apple ground-truth dataset, per-OS validation, unknown-class behavior, and drift monitoring exist.

**Tests:** checked-in minimal synthetic packet fixtures with no personal identifiers; truncated/malformed packets; DHCP-only join; SSDP `LOCATION` retained as redacted metadata but never fetched; spoofed LLMNR; NBNS suffix parsing; randomized MAC suppresses OUI; universal MAC produces only vendor; conflicting IP/MAC mappings; expired fusion windows; capture permission failure; BPF construction; raw-payload non-retention.

Phase B may increase coverage when Bonjour is quiet and is valuable for detecting a third-party AirPlay implementation whose other views disagree. It may still see nothing on an isolated WLAN or outside a lease event, so it remains optional evidence rather than a prerequisite.

### Phase C — opt-in nearby radio and native Apple P2P

**Goal:** observe eligible nearby Apple ecosystem activity with explicit consent and tight retention.

1. Implement `native_dnssd.py` (or a small Swift helper with a JSON-lines boundary) using `DNSServiceBrowse`/`DNSServiceResolve` and explicit `IncludeP2P` / `IncludeAWDL` flags. Expose `scan --nearby-p2p` separately from normal LAN browsing. Prefer Apple's daemon/API; do not parse/inject raw AWDL action frames or depend on private driver controls.
2. Implement BLE only as `scan --nearby-ble` in a signed native helper/app host that provides the Bluetooth purpose string and permission UX. Scan advertisements without connecting. Emit coarse evidence (`apple_manufacturer_advertisement`, Continuity type if validated), rotating address, timestamp bucket, and RSSI bucket; never emit contact hashes or attempt decryption.
3. Keep infrastructure, AWDL/P2P, and BLE records visibly separate. Merge only when explicit contemporaneous data warrants it, and display the merge reason. Add hard duration/device-count caps and a prominent proximity/privacy notice.

**Tests:** mocked native callbacks; correct flags and default exclusion; permission denied/restricted/powered-off states; activity-dependent disappearance; separate planes with same name; rotating BLE addresses not treated as stable identity; no GATT connect; no AWDL activation/injection; cancellation and deadline cleanup.

Phase C has high situational coverage but the highest platform, consent, and privacy cost. It should not be an implicit fallback when Phase A is empty.

## Privacy, ethics, and retention

Local discovery data can reveal owner names, rooms, routines, device presence, and stable identifiers. Yu et al. found personal names in device-name fields and retained only truncated MAC prefixes after removing names; Stute et al. demonstrated that AWDL hostnames/mDNS could enable user tracking. Apple now randomizes infrastructure and peer-to-peer Wi-Fi addresses specifically to reduce tracking ([Apple Platform Security](https://support.apple.com/en-lamr/guide/security/sec31e483abf/web)). A diagnostic tool should not rebuild the cross-context identifiers those protections are intended to prevent.

Operational safeguards:

- collect only on networks and in physical spaces the operator is authorized to observe;
- state whether the mode sends DNS-SD queries or is wire-passive, and require an explicit flag for privileged packet or nearby-radio modes;
- use a bounded default duration; no daemon, history, cloud upload, telemetry, or cross-run device database;
- keep correlation keys in memory with a per-run salt; discard the salt at exit;
- suppress or redact owner/device names, full MACs, DHCP IDs/DUIDs, HomeKit IDs, BLE addresses, contact-derived values, and raw TXT bytes from routine output;
- retain only the minimum evidence needed to explain a result: sanitized service/field name, model identifier when explicitly needed, coarse category, source plane, and timestamp bucket;
- do not save pcap or BLE advertisement streams unless the user names an output path and acknowledges that it may contain personal data; document secure deletion/retention expectations;
- treat an identifier as a claim by a network peer, not authentication or proof of ownership; and
- avoid active validation. A false claim should produce conflict/unknown, not trigger a probe of the device.

The ethical endpoint is an explainable, ephemeral inventory assistant—not a tracker. Broader collection is justified only when each added view improves uncertainty reporting and spoof detection while preserving `unknown` as the default for unsupported precision.
